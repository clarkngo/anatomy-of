Anatomy of an agentic loop

A loop bench: the model reads the whole context stack, issues one action, the tool runs, and the result is lifted back onto the stack, until the model answers or the step counter halts it. How a single tool call is checked is the guardrail's job.

Try this: Pick “never finishes” and step through it: the tool keeps failing and only the halt gate stops the loop. Then raise max_steps to 12 and watch the stack pass the window and push the goal out.

The context, as the model reads it

One row per sheet on the stack, with its (toy) token count. Each step the model reads all of these and nothing else.

    The parts (9), one by one

    Point at a part, or focus it, to find it in the figure. Click or press Enter to step the machine to it.

    1. 01

      The loop

      An agent is a model called over and over in a loop. Each turn it reads the goal and everything so far, chooses one action, and sees the result next turn. This plaque is the whole program; the rest of the bench is what each line does.

    2. 02

      Context stack

      Every message the model has seen: the system prompt with the tool list, the user's goal, then one sheet per step with the call and its result. Sheets are only ever added, and the model re-reads the whole stack on every step, so each step costs more than the last. The crossbar is the 800-token window (a toy size).

    3. 03

      Model

      The reading arm drops onto the stack: the model sees all of it, nothing else. It writes one action card, either a tool call or FINAL with the answer. It keeps no memory between steps: what isn't on the stack, it doesn't know.

    4. 04

      Decider

      Your code, not the model, reads the card. A tool call goes on to the tool; FINAL turns the blade and the card drops into the answer tray. That is the normal stop condition: the model says it is done.

    5. 05

      Tools

      Two made-up tools with scripted results. A tool that fails doesn't stop the loop: its error is clipped to the card like any result, and the model reads it next step and can try again (pick the tool-error task). How each call is shaped and checked is a figure of its own: see the guardrail.

    6. 06

      Step counter

      The ratchet wheel moves one tooth per model call. The raised pin is max_steps. Nothing in the model guarantees it will ever answer, so the loop needs a limit of its own: after the step at the pin, the halt gate drops and the loop stops with no answer.

    7. 07

      Halt gate

      Drops across the out slot when the step limit is reached. Pick the never-finishes task: the weather tool is down, nothing tells the model when to give up, and only this gate ends the loop.

    8. 08

      max_steps dial

      Sets the stop pin. Too low and a task that would finish is cut off before its answer (try 2 on the first task). Too high and a stuck loop runs longer, costs more, and grows the stack past the window (try 12 on the never-finishes task).

    9. 09

      Answer tray

      A FINAL card is the answer to the user, so it is not appended: the loop is over. The flag shows how the loop ended: up for an answer, down for a halt.

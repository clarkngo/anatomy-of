Anatomy of tool calling

A dispatch counter split by a wall: the app passes tool cards and a question through the slot, the model sends back a call slip instead of an answer, and only the app's cabinet runs anything. For checking a call before it runs, see the guardrail.

Try this: Step “Where is order 4417?” to the end. Then switch descriptions to vague and watch the dial turn to card 2: the answer is fluent and wrong. Switch back to clear and press Q twice for “Where is my order?”: with order_id required the model asks for the number; make it optional and it sends an empty call that fails in the app. Last, “Say thank you in French.” needs no tool at all.

The parts (10), one by one

Point at a part, or focus it, to find it in the figure. Click or press Enter to step the machine to it.

  1. 01

    Tool declarations

    The app declares each tool on a card: a name, a description in plain words, and a JSON schema for its arguments (here one field each). The cards travel with every request, alongside the question. They are only descriptions: the code behind them stays in the app's cabinet. Switch to vague descriptions and watch the model pick the wrong card.

  2. 02

    Question

    What the user asked. It goes to the model together with the tool cards, and the final answer comes back to the same tray.

  3. 03

    Context desk

    Everything the model reads lies on this desk: the tool cards, the question and, later, the tool result. The model has no other view of the world. If something isn't on the desk, the model doesn't know it.

  4. 04

    Model

    The booth has no cable and no hands. It can only write: either a call slip (a tool name and arguments, as JSON) or plain text. When it writes a call, it stops and waits; the app decides whether to run it.

  5. 05

    Selector dial

    The model's choice, made by reading the names and descriptions on the cards against the question. Stops 1–3 match the cards' corner numbers; TXT means no tool, just an answer. A question that needs no tool, or one missing a required argument, turns the dial to TXT.

  6. 06

    Call slip

    The structured call: the chosen tool's name and its arguments. The schema shapes it: the field is named order_id because the card says so, and the value is a string because the type says string. Make order_id optional and ask “Where is my order?”: an empty {} fits the schema too, and the model sends it.

  7. 07

    The slot

    The only way between the two sides. Paper goes through it, never a hand: the model's call is a request the app can read, check, refuse or run. The guardrail figure shows the check: a call that fails validation goes back to the model with its error.

  8. 08

    Function cabinet

    The app's own code, one drawer per tool, wired to the app's systems (here an orders database). It reads the call slip, runs the function with those arguments and writes down what came back, including errors. This is the only part of the counter that does anything.

  9. 09

    Result slip

    What the function returned, sent back to the model as a tool result tied to the call. It lands on the desk next to the question, so the model can read it. An error goes back the same way: the model can explain it, but not fix the function.

  10. 10

    Answer

    The model reads the question and the result and writes the final answer in plain text. It can only be as right as the tool it chose: with the wrong tool, the answer is fluent and wrong.
